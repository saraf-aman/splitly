# Roadmap — Build one step at a time

Rules for using this file:
- Work top to bottom. Always pick the **first unchecked step**.
- Each step is sized to be doable (and reviewable by the human) in a single focused session.
- Check a box (`[x]`) only once the step is actually working, not just written.
- After finishing a step, add an entry to `docs/PROGRESS.md` before ending the session.
- If a step turns out to be too big once you're in it, it's fine to split it further and update this file — just note that in PROGRESS.md.

## Phase 5 — Realtime selection screen

## Phase 8 — Multi-household support

A user currently belongs to exactly one household forever (`users/{uid}.householdId` is a single string), and every screen assumes that single global context. This phase generalizes to multiple households *before* Phase 9 builds the real home dashboard, so that dashboard is built once against a picker that already exists rather than retrofitted later. Every data-fetching hook except `useUserHousehold` (`src/lib/household.ts`) already takes `householdId` as an explicit parameter, and Firestore rules already gate everything per-household via the `members` subcollection (never via the `users/{uid}` doc) — so this is additive routing + a data-shape change, not a rewrite of Phases 1-7.

- [x] **8.1** Data model: `users/{uid}.householdId: string` → `householdIds: string[]`. Update `createHousehold`/`joinHousehold` to append (`arrayUnion`) instead of overwrite.
- [x] **8.2** `leaveHousehold` action + rule change: today even self-removal requires `isHouseholdAdmin`, so a guest cannot leave on their own. Add a rule clause letting any non-creator member delete their own `members/{uid}` doc regardless of role, then remove that id from their own `householdIds` array client-side — multi-household makes leaving a normal action, not an exceptional one.
- [x] **8.3** Hooks rework: replace `useUserHousehold()` with `useUserHouseholds()` (returns the list the user belongs to). Every other hook (`useHousehold`, `useMembers`, `useMembershipStatus`, `updateMemberRole`, `removeMember`, `deleteHousehold`) is unchanged.
- [x] **8.4** Routing rework: flat routes (`/`, `/bills/new`, `/household`) become `/households/[householdId]/...`.
- [x] **8.5** Picker/landing screen: lists all of the user's households (reuses the existing create/join UI as "add another household"); if the user belongs to exactly one, auto-enter it directly rather than forcing an extra tap.
- [x] **8.6** `HouseholdGate` rework: binary onboarding/home redirect becomes three-way — 0 households → `/onboarding`; exactly 1 → straight into that household; 2+ → the picker. Generalize the existing removed-while-viewing detection (currently keyed off one global `householdId`) to work per-household.

- [x] **11.7** Duplicate push notifications: every notification arrives twice on the receiving device. **Diagnose first** before fixing — two likely root causes: (a) `fcmTokens` array on the member doc has more than one entry because `arrayUnion` accumulates tokens across installs/sessions and old tokens may still be valid (FCM keeps them alive for a while before marking unregistered), so `sendEachForMulticast` fires once per token; (b) on iOS the PWA home-screen install and Safari browser each register a separate service worker context → separate FCM token → both stored in the array → two deliveries to what the user experiences as one device. **Confirm it's a server-side duplicate (not client-side):** check the Vercel function logs for `/api/notify-bill-open` and `/api/notify-settle` — if the log shows `sent: 2` for a member who should only get one notification, cause (a) or (b) is confirmed. ## Phase 12 — Participant scoping, manual entry & completion notifications

Full design spec in `docs/PROJECT_PLAN.md §15`.

- [x] **12.1** Bill participant scoping — data model + upload-time picker: add `bills/{billId}.participantIds: string[]` (only members in this list can see/access the bill). Upload screen (`/bills/new`) gets a checklist of household members, all pre-checked; uploader unchecks anyone not involved before confirming. `firestore.rules` bill-level `read/update/delete` gated on `request.auth.uid in resource.data.participantIds` instead of plain household membership (uploader is always included in `participantIds` at creation). Home feed query filters out bills the current user isn't a participant on.
- [x] **12.2** Bill participant scoping — add/remove after creation: uploader-only (not admin) control, via a "Manage participants" button on the **grid** page only (the bill's existing management hub — not review/select). Staged like the settle sheet: checkbox taps only update local state; nothing writes or notifies until "Save" is tapped, then the diff between old/new participant lists drives one `participantIds` write plus a push per changed member (added → "tap to select your items"; removed → notified they no longer have access). Removing someone is only allowed if that member has made zero selection changes on the bill (still at all-default `included:true, shares:1` for every item, and hasn't hit Confirm) — if they've interacted, block the removal with a warning-styled dialog: *"[Name] has already made selections on this bill. Ask them to either reset their picks, or clear their selections yourself."* (the uploader can already edit any member's selections via the Phase 6.4 grid override).
- [x] **12.3** Manual bill entry: add a "Enter manually" option alongside the existing camera/file-picker choice on `/bills/new`. Skips the Gemini parsing call entirely — uploader types item name + price rows directly (same shape the AI parser would have produced), then proceeds into the existing review/confirm flow unchanged. Creates the bill doc with status `pending_review` same as the AI path so nothing downstream needs to know which path was used.
- [x] **12.4** "Everyone's done" notification: when the last participant (per `participantIds` from 12.1, uploader included if they're a participant) flips their Phase 5.4 "confirm my selections" indicator to done, trigger a push to the uploader only: *"Everyone's made their picks on [bill name] — check the final split and push to Splitwise."* Reuses the existing FCM send path from Phase 7.2. Only sent if the uploader hasn't already pushed the bill to Splitwise, and sent at most once per bill.
- [x] **12.5** Automated reminder nudges: scheduled Vercel cron (`/api/cron/remind-bills`, `CRON_SECRET`-authenticated, daily) scans `open` bills and pushes a reminder to any participant (excluding the uploader) who hasn't hit "confirm my selections" yet. Cadence per bill per member: first reminder 24h after the bill opened, then every 72h after that (e.g. bill opens Sunday → reminders Monday, Thursday, Sunday), capped at 3 total reminders — after the cap, that member goes silent until they act or the uploader manually nudges (12.6). Track state on the bill doc: `reminders.{uid}: { count: number, lastSentAt: timestamp }`.
- [x] **12.6** Manual "remind" action, final design (deviates from original wording below per user feedback — no bulk button on the main grid): a small per-member "Remind" icon inside the "Manage settlement" sheet (opened from the confirmed-members banner, grid page only), shown next to each not-yet-confirmed member's row, visible to the bill uploader only. Tapping it pushes a reminder to just that member, rate-limited to once per 24h **per member** via `bills/{billId}.manualReminderSentAt.{uid}` — that member's icon shows a "Xh" cooldown state until it clears (other members' icons are unaffected).
- [x] **12.7** Group retention policy, final design (deviates from original wording below per user direction): lives only in the Manage group page (`/groups/[groupId]/group`), creator-only (not admin-changeable, not on the group creation form). Options: 1, 3, 6, 12 months, or Never. Stored as `retentionMonths: number | null` on the household doc (`null` = never hide). Client-side feed filter uses this value (replaced the hardcoded 30-day filter in `groups/[groupId]/page.tsx`) — settled bills older than the retention threshold are hidden from the feed immediately, regardless of whether the cron (12.8) has deleted them yet. Existing pre-12.7 groups were migrated to `retentionMonths: 6` so their hide behavior didn't silently change from ~30 days to never. **Updated later:** new groups now default to `retentionMonths: 6` at creation (`createGroup` in `src/lib/group.ts`), not Never — per user direction, so new groups match the same behavior as migrated existing ones instead of accumulating settled bills forever by default. Still creator-changeable in Manage, including back to Never.
- [x] **12.8** Vercel cron — server-side bill deletion: `/api/cron/cleanup-bills` route, authenticated via Vercel's `CRON_SECRET`. Runs daily. Uses Firebase Admin SDK to fetch all groups with a non-null `retentionMonths`, queries settled bills older than their threshold, and batch-deletes each bill doc + its subcollections (items, sharedCharges — selections live inline on item docs, not a separate subcollection). Groups with `retentionMonths: null` ("Never") are skipped. Double-tier with 12.7: the client-side hide is the first layer (instant, free), the cron delete is the second layer (async cleanup). If the cron hits Firestore's free-tier daily write/delete quota, it stops and retries the next day — users never see the stale bills either way because the hide layer already filtered them.
- [x] **12.9** General mobile polish pass, offline/error state handling, loading states.
